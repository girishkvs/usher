# Releasing

How a change gets from this repository into the Edge Add-ons store.

## The short version

```powershell
# 1. bump the version in package.json and add a CHANGELOG entry
npm run verify          # typecheck, unit tests, licence gate, build, bundle checks
npm run test:e2e        # browser suite, on Edge and on Chrome
npm run screenshots     # only when the UI changed
npm run pack            # artifacts/usher-<version>.zip

git commit -am "Release 1.2.0"
git tag v1.2.0
git push origin main --tags
```

Pushing the tag runs `.github/workflows/release.yml`, which verifies, packs,
attaches the zip to a GitHub release, and — once the store credentials exist —
submits it to Edge Add-ons.

## The version number is the contract

`dist/manifest.json` takes its version from `package.json` at build time. The
template at `public/manifest.json` deliberately carries no `version` field, so
there is only ever one copy of the number and nothing to drift; the build fails
if that field reappears. The release workflow additionally refuses to run if
the git tag does not match the built manifest, which is what stops a `v1.2.0` tag
from shipping a package that still says `1.1.0`.

Edge requires the version to increase on every submission. A resubmission after a
rejection therefore needs a new version, not a re-upload of the old one.

## First submission: by hand

The API can only update a product that already exists, because every call is
addressed to a product id. Version 1.0.0 goes up manually:

1. Create a Partner Center account (free) and register as an Edge extension
   developer.
2. **Submit new extension**, upload `artifacts/usher-1.0.0.zip`.
3. Fill in the listing from [store-listing.md](store-listing.md): description,
   screenshots from `build/store/`, privacy policy URL, and the per-permission
   justifications. The justifications matter — `<all_urls>` gets a human reviewer.
4. Submit, and wait for certification. Expect a few days.
5. Once it is live, copy the **Product ID** from the extension's Partner Center
   page.

## Every release after that: automated

Enable the API and store the credentials once:

1. Partner Center → **Publish API** → opt in, then create an API key.
2. In GitHub → Settings → Secrets and variables → Actions, add:

   | Kind | Name | Value |
   |---|---|---|
   | Secret | `EDGE_PRODUCT_ID` | Product ID from Partner Center |
   | Secret | `EDGE_CLIENT_ID` | Client ID shown beside the API key |
   | Secret | `EDGE_API_KEY` | The API key itself |
   | Variable | `EDGE_ENABLED` | `true` |

The `EDGE_ENABLED` variable is a deliberate switch: the publish step is skipped
until you turn it on, so tagging never surprises you with a store submission.

Then a release is just:

```powershell
git tag v1.2.0
git push origin v1.2.0
```

To upload a package without submitting it for review, run
`node scripts/publish-edge.mjs --no-publish` and finish in Partner Center.

> [!IMPORTANT]
> Edge Add-ons API keys expire every **72 days** and have to be regenerated by
> hand in Partner Center. There is no endpoint for rotating them. When a release
> fails with a 401, that is almost always why.

## What is in the package

`npm run pack` zips `dist/`, which is the built extension and nothing else:
compiled bundles, the manifest, HTML, CSS, icons, the network rules, and
`THIRD-PARTY-NOTICES.txt`. Sources, tests, screenshots, and `node_modules` are
not included.

## What is not in git

`dist/`, `build/`, `artifacts/`, and `node_modules/` are all ignored. The store
assets in `build/store/` are regenerated with `npm run screenshots` rather than
committed, so they cannot drift from the product.

## Chrome

The same package works unchanged in the Chrome Web Store. It is not published
there only because registration charges a one-off fee. If that changes, add a
Chrome step to the release workflow; the 1280x800 screenshots are already
generated for it.
